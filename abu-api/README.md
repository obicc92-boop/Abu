# Abụ API (Cloudflare Worker)

One Worker, `abu`, at https://abu.adalingo.workers.dev:

- **Website:** the web build of `../abu-app` (`dist/`), served as static assets. Pages and files never run Worker code.
- **API:** everything under `/api/*`, built with [Hono](https://hono.dev).
- **Database:** D1 database `abu` (Western Europe, the closest location D1 offers to Nigeria), schema in `migrations/`.

## Run

```sh
npm install
npm test             # access rules and API, inside the Workers runtime with a local D1
npm run typecheck
npm run dev          # local Worker on http://localhost:8787 (build ../abu-app first for the pages)
npm run deploy       # build the web app, apply D1 migrations, deploy the Worker
npm run types        # regenerate worker-configuration.d.ts after changing wrangler.jsonc
```

Wrangler uses the Cloudflare account it's signed in to on this Mac. Tests never touch the real account.

### Sign-in

- **Engine:** [Better Auth](https://www.better-auth.com) on the Worker (`src/auth.ts`), with its tables in D1 (`migrations/0002_sign_in.sql`, generated by Better Auth itself). Email and password for now; email codes and Google attach later.
- **Passwords:** hashed with PBKDF2 from the Workers runtime's Web Crypto. Better Auth's default hashing costs too much CPU for a Worker.
- **Sessions:** last 90 days on a phone.
- **Production secret:** `BETTER_AUTH_SECRET` is a Worker secret, set with `npx wrangler secret put BETTER_AUTH_SECRET`. `BETTER_AUTH_URL` is in `wrangler.jsonc`; change it when Abụ gets its own domain.
- **Local dev:** put both in `.dev.vars` (git-ignored), apply migrations with `npx wrangler d1 migrations apply abu --local`, and run `npx wrangler dev --port 8790`. Port 8787 is often taken by another project on this Mac.

## Who can see and change what

D1 has no row-level security, so every action in `src/domain/` checks access first (`src/domain/access.ts`). The rules come from the owner's decisions in `../CLAUDE.md`:

- Joining with a code is instant, unless the leader switches on approval. Someone waiting sees only the group's name.
- Only leaders change roles, approve members, plan services and song orders, and build the repertoire.
- Leaders mark anyone's attendance; part leaders mark only their own part.
- Self check-in needs the 4-digit code, which only leaders and part leaders can show. It works from 3 hours before the start to 6 hours after, and locks after five wrong codes.
- Practice is private. Leaders and part leaders see only totals per part (`partReadiness`).
- Songs are public, even signed out. Whoever shared a song, or anyone in the group it came from, can edit it.

The database itself guarantees what must never break: a group always keeps a leader, a song in a song order can't be deleted, and values stay valid.

`test/rules.test.ts` runs all of this as the prototype's personas (Emeka the choirmaster, Chiamaka the soprano part leader, and so on).

## Layout

- `src/index.ts`: the Hono app.
  - Open to everyone: `/api/health`, `/api/songs`, `/api/songs/:id`, and sign-in at `/api/auth/*`.
  - Signed in: `/api/me`, `/api/groups` (create), `/api/groups/preview/:code`, `/api/groups/join`, `/api/groups/:id` (read and settings), and `/api/groups/:id/members` (list, approve, role and part, remove or leave).
  - Songs, open to everyone: `GET /api/songs` (filters `q`, `tag`, `playable=1`), `GET /api/songs/:id`, and `GET /api/songs/:id/sheet` (the original sheet).
  - Songs, signed in:
    - sharing, editing and deleting: `POST /api/songs`, `PATCH` and `DELETE /api/songs/:id`
    - the sheet: `PUT` (body = the file; PDF, JPEG, PNG or WebP up to 10 MB) and `DELETE /api/songs/:id/sheet`
    - what you can do with a song: `GET /api/songs/:id/me`
    - practice: `POST /api/songs/:id/plays`, `PUT /api/songs/:id/knows`, `GET /api/me/practice`
  - Repertoire: `GET`, `POST /api/groups/:id/repertoire` and `DELETE /api/groups/:id/repertoire/:songId`. Your own space's repertoire is "My songs".
  - Everything else in `src/domain` gets routes with its milestone.
- `src/domain/`: groups and people, songs and repertoire, events and replies, attendance and check-in, practice, notices.
- `src/errors.ts`: errors with an HTTP status and a message safe to show people.
- `src/auth.ts`: sign-in.
- Sol-fa: `src/domain/songs.ts` imports the app's reader from `../abu-app/src/solfa`, so a song is checked by the same code on both sides. Keep that module free of app-only imports.
- Original sheets: R2 bucket `abu-sheets` (binding `SHEETS`), under `sheets/<song id>/`.
- `migrations/`: D1 migrations, applied by `npm run deploy` (or `npm run db:migrate`).
- `test/`: access rules (`rules.test.ts`), sign-in and onboarding over HTTP (`auth.test.ts`), and the public endpoints (`http.test.ts`).
