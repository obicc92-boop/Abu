# Abụ API (Cloudflare Worker)

One Worker, `abu`, at https://abu.adalingo.workers.dev:

- **Website:** the web build of `../abu-app` (`dist/`), served as static assets. Pages and files never run Worker code.
- **API:** everything under `/api/*`, built with [Hono](https://hono.dev).
- **Database:** D1 database `abu` (Western Europe, the closest location D1 offers to Nigeria), schema in `migrations/`.

## Run

```sh
npm install
npm test             # access rules and API, inside the Workers runtime with a local D1
npm run typecheck
npm run dev          # local Worker on http://localhost:8787 (build ../abu-app first for the pages)
npm run deploy       # build the web app, apply D1 migrations, deploy the Worker
npm run types        # regenerate worker-configuration.d.ts after changing wrangler.jsonc
```

Wrangler uses the Cloudflare account it's signed in to on this Mac. Tests never touch the real account.

### Sign-in

- **Engine:** [Better Auth](https://www.better-auth.com) on the Worker (`src/auth.ts`), with its tables in D1 (`migrations/0002_sign_in.sql`, generated by Better Auth itself). Email and password for now; email codes and Google attach later.
- **Passwords:** hashed with PBKDF2 from the Workers runtime's Web Crypto. Better Auth's default hashing costs too much CPU for a Worker.
- **Sessions:** last 90 days on a phone.
- **Production secret:** `BETTER_AUTH_SECRET` is a Worker secret, set with `npx wrangler secret put BETTER_AUTH_SECRET`. `BETTER_AUTH_URL` is in `wrangler.jsonc`; change it when Abụ gets its own domain.
- **Local dev:** put both in `.dev.vars` (git-ignored), apply migrations with `npx wrangler d1 migrations apply abu --local`, and run `npx wrangler dev --port 8790`. Port 8787 is often taken by another project on this Mac.

### Scanning sheets

- **The app does most of the reading itself** (typed PDFs from their text, lines in pictures found by ink and read by Abụ's own model). The Worker's readers (`src/scan.ts`) are for what's left, in this order:
  - **Cloudflare's reader** (the `AI` binding, Workers AI, Mistral Small 3.1, plain-text answers): corrects a line that fails the checker, and reads rows of words in pictures. On the Workers Free plan it stops for the day after 10,000 neurons; that skips it (503) rather than stopping the scan. AI bindings always reach Cloudflare, even in `wrangler dev`, and are billed to the account.
  - **Claude**, only with a key (Anthropic SDK, fixed JSON schemas): Haiku checks a line, Opus reads it from scratch, and Haiku finds the lines on a page the app couldn't.
- **Optional secret:** `ANTHROPIC_API_KEY`, set with `npx wrangler secret put ANTHROPIC_API_KEY`. Without it, Claude's routes answer "Claude isn't switched on for scanning" before anything is counted, and scanning works without them.
- **Optional gateway:** set `ANTHROPIC_BASE_URL` to send the calls through Cloudflare AI Gateway instead of straight to Anthropic.
- **Local dev:** the key can go in `.dev.vars`. Tests always run without it (`vitest.config.ts`), so they never reach Claude.
- **Daily allowance** (`src/domain/scan.ts`, table `scan_usage`): 40 pages and 400 lines per person, and 2,000 lines for everyone together, about US$30 at most.

## Who can see and change what

D1 has no row-level security, so every action in `src/domain/` checks access first (`src/domain/access.ts`). The rules come from the owner's decisions in `../CLAUDE.md`:

- Joining with a code is instant, unless the leader switches on approval. Someone waiting sees only the group's name.
- Only leaders change roles, approve members, plan services and build the repertoire.
- Leaders edit song orders. Part leaders can too when a leader switches on `part_leaders_edit_orders` ("Part leaders can edit song orders"); see `requireOrderEditor` in `src/domain/access.ts`.
- Leaders mark anyone's attendance; part leaders mark only their own part.
- Self check-in needs the 4-digit code, which only leaders and part leaders can show. It works from 3 hours before the start to 6 hours after, and locks after five wrong codes.
- Practice is private. Leaders and part leaders see only totals per part (`partReadiness`). Your week and streak (`practiceSummary`) are only ever yours.
- Notices: leaders and part leaders post, to everyone or one part; part leaders only to everyone or their own part. Leaders pin; the author or a leader deletes.
- Attendance rates: leaders and part leaders see everyone's (`attendanceReport`); members see only their own (`myAttendance`). A rate is present out of present and absent, so excused (and "Can't come") never counts against anyone.
- Songs are public, even signed out. Whoever shared a song, or anyone in the group it came from, can edit it.

The database itself guarantees what must never break: a group always keeps a leader, a song in a song order can't be deleted, and values stay valid.

`test/rules.test.ts` runs all of this as the prototype's personas (Emeka the choirmaster, Chiamaka the soprano part leader, and so on).

## Layout

- `src/index.ts`: the Hono app.
  - Open to everyone: `/api/health`, `/api/songs`, `/api/songs/:id`, and sign-in at `/api/auth/*`.
  - Signed in: `/api/me`, `/api/groups` (create), `/api/groups/preview/:code`, `/api/groups/join`, `/api/groups/:id` (read and settings), and `/api/groups/:id/members` (list, approve, role and part, remove or leave).
  - Songs, open to everyone: `GET /api/songs` (filters `q`, `tag`, `playable=1`), `GET /api/songs/:id`, and `GET /api/songs/:id/sheet` (the original sheet).
  - Songs, signed in:
    - sharing, editing and deleting: `POST /api/songs`, `PATCH` and `DELETE /api/songs/:id`
    - the sheet: `PUT` (body = the file; PDF, JPEG, PNG or WebP up to 10 MB) and `DELETE /api/songs/:id/sheet`
    - what you can do with a song: `GET /api/songs/:id/me`
    - practice: `POST /api/songs/:id/plays`, `PUT /api/songs/:id/knows`, `GET /api/me/practice`
  - Repertoire: `GET`, `POST /api/groups/:id/repertoire` and `DELETE /api/groups/:id/repertoire/:songId`. Your own space's repertoire is "My songs".
  - Schedule (members read and reply; leaders plan):
    - `GET /api/groups/:id/events` (optional `from` and `to`) and `POST` (with `repeat_weeks` for weekly rehearsals); `GET /api/groups/:id/song-history` (when each song was last sung)
    - `GET`, `PATCH` and `DELETE /api/events/:id`; the details include the order, your reply and the reply counts
    - the order: `POST /api/events/:id/items`, `DELETE /api/events/:id/items/:itemId`, `PUT /api/events/:id/order` (the whole order with its sections, in one go; refused if songs were added or removed meanwhile), `POST /api/events/:id/copy-order`
    - replies: `PUT /api/events/:id/reply`, `GET /api/events/:id/replies`
    - readiness per part, totals only, for leaders and part leaders: `GET /api/events/:id/readiness`
  - Attendance (leaders and part leaders, except your own check-in and rate):
    - the register: `GET /api/events/:id/attendance`, `PUT /api/events/:id/attendance/:userId`, `POST /api/events/:id/attendance/rest` (mark everyone unmarked present or absent)
    - self check-in: `GET /api/events/:id/check-in-code`, `POST /api/events/:id/check-in`
    - rates: `GET /api/groups/:id/my-attendance` (yours), `GET /api/groups/:id/attendance` and `.../attendance.csv` (the report; optional `from`, `to` and `tz`, the viewer's `getTimezoneOffset()`)
  - Notices: `GET` and `POST /api/groups/:id/notices` (`body`, optional `part`), `PUT /api/notices/:id/pin`, `DELETE /api/notices/:id`.
  - The leader's To do: `GET /api/groups/:id/todo` (leaders; part leaders for their part).
  - Your practice week: `GET /api/me/practice/summary?today=YYYY-MM-DD`; `POST /api/songs/:id/plays` takes the phone's `day`.
  - Changing your password is Better Auth's own `POST /api/auth/change-password`.
  - Scanning (signed in):
    - `POST /api/scan/page?w=&h=` (body = a JPEG, PNG or WebP of a page, up to 5 MB) finds the lines of music, in the picture's pixels, plus the title, composer, key and time.
    - `POST /api/scan/line?parts=S,A,T,B&time=&key=` (body = a picture of one line) reads it into sol-fa, with the words and the bars to check first.
    - `POST /api/scan/check?parts=S,A,T,B&draft=&time=&key=` (body = a picture of one line; `draft` = the own model's reading, up to 4,000 characters) has Haiku correct the draft against the picture. Same answer as `/scan/line`, and it counts as a line.
    - `POST /api/scan/fix?parts=S,A,T,B&draft=&time=&key=` (body = a picture of one line) has Cloudflare's reader correct the draft. Same answer as `/scan/line`; counts as a line.
    - `POST /api/scan/words` (body = a picture of one row of words) returns `{ words }`, read by Cloudflare's reader; counts as a line.
    - `GET /api/scan/allowance` returns what's left today, and `readers: { cloudflare, anthropic }`, which the app tries in that order.
- `src/domain/`: groups and people, songs and repertoire, events and replies, attendance and check-in, practice, notices.
- `src/errors.ts`: errors with an HTTP status and a message safe to show people.
- `src/auth.ts`: sign-in.
- Sol-fa: `src/domain/songs.ts` imports the app's reader from `../abu-app/src/solfa`, so a song is checked by the same code on both sides. Keep that module free of app-only imports.
- Original sheets: R2 bucket `abu-sheets` (binding `SHEETS`), under `sheets/<song id>/`.
- `migrations/`: D1 migrations, applied by `npm run deploy` (or `npm run db:migrate`).
- `src/scan.ts`: the AI help for scanning (Cloudflare's reader, then Claude): the prompts, the answer schemas, and shaping the answers.
- `test/`: access rules (`rules.test.ts`), sign-in and onboarding over HTTP (`auth.test.ts`), and the public endpoints (`http.test.ts`).
